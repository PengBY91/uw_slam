# HoloOcean tick 预算实测（PREP-A-01，2026-09-02）

- 主机：Windows 11，RTX 4070 Laptop 8 GB，HoloOcean 2.3.0 `Ocean` 包，`PierHarbor` 世界，`blue_rov_aid_sv1213_base.json` 派生配置
- 方法：`adapters/holoocean/tools/tick_budget.py`（从 WSL2 经 `powershell.exe` 调用），每个配置预热 40 tick，计时 300/400 tick，推进器命令为零，GPU 由 `nvidia-smi` 在中段采样一次
- 原始数据：同目录 `tick_budget_round1_2026-09-02.json`、`tick_budget_round2_2026-09-02.json`

## 第一轮：基线 `frames_per_sec: 20` 上限下的合同机器配置

| 配置 | ticks/s | ms/tick 均值 (p95) | RTF | GPU 显存 MiB / 占用 % | 传感器 |
|---|---|---|---|---|---|
| a 当前基线：双目 720p@20 + 飞手相机 + 声呐 10 Hz 768×512 | 19.4 | 51.6 (75.3) | 0.19 | 3255 / 96 | 3 路 1280×720@20；声呐 10 Hz；IMU 50 |
| b 单目 960×540@20 + 声呐 10 Hz | 20.0 | 49.9 (50.8) | 0.20 | 2840 / 40 | |
| c 单目 1920×1080@30 + 声呐 10 Hz | 20.0 | 49.9 (52.0) | 0.20 | 3428 / 71 | 相机实际 33.4 Hz（量化到 100/3） |
| c 无声呐 | 20.0 | 49.9 (51.8) | 0.20 | 3268 / 52 | |
| d 单目 1080p@30 + 声呐 40 Hz 768×512 | 20.0 | 50.0 (52.2) | 0.20 | 3429 / 52 | 声呐实际 50.2 Hz（量化到 100/2） |
| e 单目 1080p@30 + 声呐 20 Hz 768×256 | 19.6 | 51.1 (58.4) | 0.20 | 3445 / 66 | |

**结论 1**：六种配置全部精确卡在 20 ticks/s、50 ms/tick，与 GPU 占用无关——这是场景文件 `frames_per_sec: 20` 的墙钟帧率上限（HoloOcean 文档：`true` 跟随 `ticks_per_sec`，`false` 不限，数字为上限）。之前记忆里"实测 12–13 Hz"是在别的负载下的数字，本次没有复现。
**结论 2**：传感器 Hz 被量化为 `ticks_per_sec` 的整数分频（`scenario_manifest.py` 已强制"Hz 必须整除 ticks_per_sec"，本脚本绕过了校验才暴露出来）。合同机器的 IMU 200 Hz 意味着 `ticks_per_sec` 至少 200；30 fps 相机在 100 或 200 ticks 下都不可精确表示（要 25 或 40）。

## 第二轮：`frames_per_sec: false`（不限）下的真实上限

| 配置 | ticks/s | ms/tick 均值 (p95) | RTF | GPU 显存 MiB / 占用 % |
|---|---|---|---|---|
| u1 t100，单目 1080p@25，声呐 10 Hz 768×512 | 26.3 | 38.0 (87.8) | 0.26 | 3441 / 78 |
| u2 t100，**无相机**，声呐 10 Hz 768×512 | 45.9 | 21.8 (26.2) | 0.46 | 2936 / 98 |
| u3 t100，单目 960×540@25，声呐 20 Hz 768×256 | 24.4 | 41.1 (71.9) | 0.24 | 3025 / 95 |
| u4 **t200**，单目 1080p@25，声呐 20 Hz 768×512，IMU 200 Hz | 21.2 | 47.1 (105.7) | **0.11** | 3278 / 97 |
| u5 t100，单目 1080p@25，声呐 25 Hz 768×512 | 21.0 | 47.6 (95.8) | 0.21 | 3270 / 64 |

由各配置均值反推的单项开销（近似，按"每仿真秒墙钟时间 = ticks × 基础 + 帧数 × 单帧"线性拆分）：

| 项目 | 近似开销 |
|---|---|
| 无渲染的基础 tick（物理 + 引擎帧 + IPC） | ≈15 ms/tick |
| 1080p 相机一帧 | ≈65 ms |
| 960×540 相机一帧 | ≈40 ms（u3 反推，含 256 bin 声呐的混杂） |
| 声呐 768×512 一帧 | ≈60–65 ms |
| 声呐 768×256 一帧 | ≈30–40 ms |

**结论 3**：GPU 显存不是瓶颈（峰值 3.4 GB / 8 GB）；瓶颈是每 tick 约 15 ms 的固定开销（不限帧率、无相机时也只有 46 ticks/s）加上相机/声呐每帧 60 多毫秒的渲染。
**结论 4**：`SIM-TIME-005` 要求标称配置 RTF P95 ≥ 1.0，**本机在任何接近合同传感器速率的配置下都达不到**。按上表估算合同速率（1080p 25–30 Hz、声呐 40 Hz 768×512、IMU 200 Hz → ticks 200）：200×15 + 30×65 + 40×62 ≈ 7.4 s 墙钟/仿真秒，RTF ≈ 0.13，与 u4 实测 0.11 一致。
**结论 5**：要 RTF ≥ 1 只能大幅降低 tick 率和帧率，例如 `ticks_per_sec: 25`、相机 960×540@12.5 Hz、声呐 5 Hz 768×256：25×15 + 12.5×40 + 5×35 ≈ 1.05 s/仿真秒，勉强到 1.0，且 IMU 在仿真里只有 25 Hz。这是"飞手训练/实时 HMI 演示"档，不是算法验证档。

## 对规格的影响

- 仿真运行分两个 profile，写入 `SIM-PERF-001..003`：
  - **fidelity**（算法验证、录制回放）：`ticks_per_sec: 200`、`frames_per_sec: false`，IMU 200 Hz、相机 25 Hz 1080p、声呐 40 Hz；RTF ≈ 0.1，所有时间戳用仿真时间，管线走 PREP-A-13 的外部时钟源模式；60 秒仿真约 10 分钟墙钟。
  - **realtime**（飞手训练、HMI 演示、SITL 闭环）：`ticks_per_sec: 25`、`frames_per_sec: true`，相机 960×540@12.5 Hz、声呐 5 Hz 768×256、IMU 25 Hz；RTF ≈ 1。
- `SIM-TIME-005` 的"标称配置"改指 realtime profile；fidelity profile 明确豁免 RTF 门槛。
- `blue_rov_aid_sv1213_base.json` 的 `frames_per_sec: 20` 是目前 RTF 0.2 的直接原因，A-03 建新基线时按 profile 分别设置。
- 相机 30 fps 在仿真里不可精确表示，A-03 用 25 Hz（fidelity）/12.5 Hz（realtime）。
- 台式 GPU 只能压缩 60 ms 的渲染项，压不掉 15 ms 的 tick 固定开销；提升 fidelity profile 的 RTF 更有效的办法是降低 `ticks_per_sec`（把 IMU 仿真频率降到 100 Hz 可让 RTF 提高约一倍）。
