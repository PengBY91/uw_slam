# `uw_slam` 文档一致性刷新设计

## 背景与目标

根目录 `README.md`、`CLAUDE.md` 和 `docs/` 下的当前事实文档落后于近期实现：测试规模、
真实 HoloOcean 录制与 VO 验证边界、声光场景矩阵 gate、关联器歧义修复、RunManifest
provenance、配置选择校验和相机校正能力等表述均有不同程度的失效。本次刷新以
2026-08-22 的当前工作树为事实对象，全面消除这些文档中的过时状态说明，同时保留带日期
设计文档的历史决策背景。

完成后，新读者应能从 README 正确认识项目成熟度，开发者应能从 CLAUDE 获得有效约束，
专题文档之间对“已实现、已验证、计划中”的判断应保持一致。

## 事实源与核对基准

事实按以下优先级核对：

1. 当前工作树中的源码、schema、配置和测试；
2. 实际构建、测试收集和验证命令输出；
3. 当前 `HEAD` `8df083b` 及其近期提交记录；
4. 已有当前事实文档；
5. 长期架构与历史 Pipeline 方案。

工作树中已有未提交的 P1 相机校正与配置校验改动。这些改动属于用户工作，不由本任务
创建或回退；只在其实现和测试足以确认时写入文档，并明确区分“工作树已实现”与
“已由提交基准验证”。如果实施期间这些文件继续变化，最终核对以验证时看到的工作树为准。

构建和测试数量不从旧文档复制。CTest 数量由重新配置/构建后的 `ctest -N` 或实际测试
结果确定，Python 数量由 pytest 收集或实际运行结果确定。容易变化的数字同时注明“以实跑
为准”，避免将瞬时统计写成稳定接口。

## 文档更新设计

### 根 README

README 继续承担项目定位和最快上手入口，不扩写成代码参考。更新内容包括：

- 当前阶段和生产边界；
- 能力矩阵中的真实数据、双目 VO、声光融合、场景矩阵和可复现实验状态；
- 完整验证命令、当前测试规模和关键产物；
- 合成与真实 HoloOcean 数据路径各自已经验证到哪里；
- 配置字段究竟是分支选择、启动时校验，还是仍只有单一实现；
- 已知边界与延伸阅读。

README 只陈述能由代码、测试或保存的验证产物支持的能力。真实数据“能录制/能回放/能
产出 VO”不外推为实时闭环、精度达标或生产就绪。

### CLAUDE

CLAUDE 保持“修改仓库时必须知道的约束和坑”的定位。删除仓库没有提交历史等已失效
说明，更新：

- 当前 git 与提交约定；仍然保留“未经用户明确要求不要 commit”；
- 构建、CTest、pytest、lint 和端到端验证方式；
- P0 场景矩阵 coverage gate 及 fail-closed 场景语义；
- 压力深度与相机光学深度的坐标/符号区别；
- 配置选择校验、相机去畸变/校正的实际支持边界；
- 当前目录速查和近期已确认的工程陷阱。

短期统计与长期不变量分开书写，避免测试数量变化后让整个开发约定失真。

### 文档中心与当前事实文档

`docs/README.md` 更新每份文档的状态、权威范围、最后核对日期和 commit/工作树说明。

新人指南按真实调用链更新入口、阅读顺序、常见修改落点和验证路径。代码库参考执行最
完整的逐节审计：类型、文件、可执行程序、配置消费、测试、真实数据链路、声光矩阵结果
和未实现项都与当前代码对齐。测试指南修正场景矩阵退出码语义、当前测试集合、真实数据
验证命令和预期结果。生产就绪路线图把 P0 已完成项标成完成，并把未完成工作留在对应的
P1–P3 阶段，不把路线图改写成纯状态报告。

### 带日期的历史设计文档

长期架构与 Pipeline 工程方案保留原始目标、阶段规划和当时的审计判断。只做三类修改：

1. 在入口状态说明中增加截至 2026-08-22 的实现进展与当前事实文档链接；
2. 修正正文中明确使用“当前仓库现在……”却已不再成立的陈述；
3. 对已经实现的计划项增加短注，不删除原始动机和设计内容。

历史预测、方案比较和延后决策不因当前实现推进而被静默重写。

## 一致性规则

- “已实现”表示当前工作树存在可达代码路径；“已验证”还必须有对应测试或实跑证据。
- 合成数据、录制的真实数据和实时仿真/ROS2 数据明确分开。
- 能录制、能解析、能回放、能估计和精度合格是五个不同声明，不互相替代。
- 场景矩阵的故障注入预期拒绝不描述为失败；coverage gate 的非零退出码描述为测试失败。
- 压力深度使用世界/载体 Z-up 下的正向下深度量，光学深度使用相机 optical frame
  正向前距离，不再笼统混称。
- 当前事实文档记录实际核对日期；引用 commit 时同时说明未提交工作树是否参与核对。
- 命令、路径、target 和配置值使用源码中的精确名称。
- 不复制组件 README 已经权威维护的安装细节，只链接到它们。

## 验证策略

实施结束后执行：

1. 重新配置和构建，确认文档所列可执行 target 与当前工作树一致；
2. 运行 CTest、Python 适配器测试和依赖 lint，记录实际结果；
3. 运行 `tools/verify_pipeline.sh`，核对 README 与测试指南中的主路径；
4. 对真实 HoloOcean 或需要外部仿真器的命令，只引用已有可复现产物和现有测试证据，
   不在缺少运行环境时伪称重新验证；
5. 扫描所有目标文档中的过时 commit、测试数量、旧状态关键词和失效路径；
6. 检查仓库内 Markdown 相对链接及其目标文件；
7. 运行 `git diff --check`，确认没有空白错误；
8. 检查最终 diff，确保未覆盖用户已有代码和配置改动。

## 验收标准

- 目标文档不再声称仓库没有提交历史。
- README、CLAUDE、文档中心、代码库参考和测试指南对测试规模及验证边界一致。
- 场景矩阵 coverage gate、歧义修复和预期拒绝场景的描述与 `8df083b` 后代码一致。
- RunManifest 已补齐与尚未补齐的 provenance 字段被准确区分。
- 真实 HoloOcean 录制/VO 与实时 ROS2 闭环的边界没有被混淆。
- 当前工作树中的配置校验和相机校正能力只按实际可达、可测试范围描述。
- 生产就绪路线图能清楚区分已完成 P0 与后续 P1–P3 工作。
- 历史设计文档仍保留原始决策背景，并清楚引导读者查看当前事实。
- 目标文档中的本地 Markdown 链接有效，命令和文件路径存在。
- 只修改批准范围内的 Markdown 文件，用户已有非文档改动保持原样。
