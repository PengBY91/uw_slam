# ROV 实时闭环规格体系设计

> 日期：2026-08-24
> 状态：设计已确认
> 决策范围：ROV 竞赛在线系统、HoloOcean 实时仿真、声光在线融合

## 1. 背景

仓库已有路线图、长期架构、真实 HoloOcean 录制规格和若干实施设计，但它们同时混合了
团队排期、当前代码事实、目标架构和离线试验方法。随着 live/replay 输入、录制行为和
硬件方案变化，文档出现了团队规模、任务范围、传感器频率和实际算法指标不一致的问题。

本设计建立三份规范性文档，把“系统必须做什么”“仿真如何证明”“在线算法链怎样工作”
分开。路线图只负责排期和资源，不再充当接口或验收规格。

## 2. 已确认决策

1. 硬件基线采用 BlueROV2 Heavy、SV1213 前视多波束声呐和 AI-D 双目相机。
2. 算法部署在水面端工控机或工作站；水下端负责传感器采集和 BlueROV2 飞控。
3. 当前基线任务为“寻找养殖区”和“按规定路径巡检水下结构物”。其他任务为规则驱动扩展。
4. 系统是遥操作 ROV 的驾驶辅助系统。首期算法不得直接控制推进器；深度与航向保持由飞控负责。
5. 首期传感器不含 DVL。BlueROV2 提供姿态、角速度、深度和设备健康。
6. 在线闭环是主验收对象；MCAP 离线回放只用于故障复盘和回归样本构造。
7. 声光融合采用“目标/航迹级主链 + 局部稠密增强”。稠密分支不得阻塞主链。
8. 实时性能使用最低放行、标称和过载三档负载，不以单一固定帧率描述全部工况。
9. 原始驾驶视频保留 BlueROV2 独立低延迟链路，AI-D 算法链不得成为操控单点故障。
10. HoloOcean 真值只进入评分器，禁止进入在线算法。

## 3. 文档体系

| 文档 | 权威范围 |
|---|---|
| `docs/specifications/rov-competition-online-system-requirements.md` | 上位目标、系统边界、硬件基线、任务、性能和整体验收 |
| `docs/specifications/holoocean-realtime-closed-loop-simulation-spec.md` | 仿真场景、传感器、时间、随机化、故障、真值隔离和仿真验收 |
| `docs/specifications/rov-acoustic-optic-online-fusion-spec.md` | 在线数据接入、缓存、同步、算法、输出、健康和降级契约 |

权威顺序为：正式赛事规则 → 在线系统需求规格 → 两份下位规格 → 路线图、实施计划、配置和
测试。代码事实与规格不一致时，必须把差异登记为缺口；不得把未实现的规格描述成当前能力。

## 4. 未采用的方案

### 4.1 单一大文档

没有采用。它会再次混合赛事范围、仿真细节和算法接口，难以维护权威边界。

### 4.2 离线回放优先

没有采用。离线确定性仍有诊断价值，但不能证明队列、调度、数据新鲜度、故障恢复和 HMI
链路在真实时间约束下成立。

### 4.3 稠密像素级融合优先

没有采用。当前竞赛任务更需要稳定的目标发现、测距、路径偏差和驾驶提示。稠密几何保留为
近距离增强能力，不作为主链前置条件。

### 4.4 完全固定或完全相对的实时指标

没有采用。完全固定的指标会在 AI-D 详细能力和目标计算机冻结前形成伪精确；完全相对的
指标又不利于采购和现场验收。三档负载同时提供硬下限、标称目标和过载行为。

## 5. 规格写作规则

- “必须/不得”表示硬要求；“应”表示有充分理由才能偏离；“可以”表示可选能力。
- 每项可验证要求使用稳定编号：`SYS-*`、`SIM-*`、`FUS-*`。
- 每项硬要求必须能够映射到测试、演练记录或采购验收证据。
- 不使用“实时、稳定、可用、精度较高”等不可判定表述替代数字和测量口径。
- 正式规则变化只修改比赛应用层任务与评分，不反向污染通用数据和融合契约。
