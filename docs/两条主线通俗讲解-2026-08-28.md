# uw_slam 两条主线通俗讲解

> 面向不需要读代码、但想理解"这套系统到底在做什么、数据怎么流转"的读者。
> 尽量把专业术语翻译成大白话，第一次出现的术语会加括号说明。
> 内容对应根目录 `README.md`「这个仓库是什么 → 两条主线」一节，并结合代码实现展开细节。
> 更偏工程细节、面向要读代码的人的版本见 `docs/uw-slam-two-mainlines-walkthrough-2026-08-26.md`。

## 先讲清楚：这套系统在解决什么问题

水下机器人（ROV，遥控无人潜水器；或 AUV，自主水下航行器）在水下没有 GPS，
要知道"我在哪、周围是什么样"，只能靠自己身上的传感器一边走一边算——这类技术统称
**SLAM**（同步定位与建图，Simultaneous Localization And Mapping）：一边估计自己的
位置和姿态（定位），一边把看到的环境拼成地图（建图）。

`uw_slam` 用两种传感器融合着做这件事：

- **声呐**（sonar）：主动发射声波、接收回波，靠"声音走了多久"算出距离。水下浑浊、
  能见度低时它比摄像头可靠，但一般只能测"多远"，测不准"多高/多低"（下面会展开）。
- **双目相机**（stereo camera，左右各一个镜头）：靠两个镜头看到同一个点的视差算距离，
  和人眼判断远近的原理一样。水清的时候看得清楚、精度高，但水浑或光线差就失效。

两者取长补短，就是标题里"声光融合"的意思（声=声呐，光=相机／视觉）。

仓库里这套融合算法有**两种跑法**，也就是"两条主线"：一种是先把数据全部录下来、
事后离线处理（像看录像回放一样，可以反复调试、精度打磨得更高）；另一种是让机器人
在水下作业时实时处理、当场给操作员提示（更像开车时的实时导航，必须又快又稳，但不
追求把每一帧都算到极致精确）。

两条主线不是各写一套代码，而是共用同一套"数据字典"（下面讲的 Protobuf 消息格式）
和同一个"数据入口"，区别只在于数据是从一个录好的文件里读出来，还是从实时传感器
流里源源不断地进来。

## 主线一：离线 SLAM 管线（成熟度最高的一条）

### 一句话概括

先把一次完整的水下作业过程（声呐帧、相机画面、深度计读数……）录成一份统一格式的
"录像文件"，然后用一条固定的处理流水线把这份录像"回放"一遍，每一步都把传感器的
原始信号变成越来越精炼的信息，最后算出机器人整趟走过的轨迹、周围环境的地图，以及
"算得准不准"的量化打分。

对应命令（`README.md`「运行端到端 Demo」一节）：

```bash
build/bin/synth_bag_gen  --experiment configs/experiment/synthetic_smoke.yaml --out /tmp/synthetic.mcap
build/bin/replay_demo    --bag /tmp/synthetic.mcap --experiment configs/experiment/synthetic_smoke.yaml --out /tmp/demo
```

第一条命令"录像"（生成数据），第二条命令"回放+处理"。下面按这两步展开。

### 第一步：数据从哪里来——统一"录成一份文件"

不管数据是真实录制的还是虚拟生成的，最终都会被整理成同一种文件格式：**MCAP**
（一种专门给机器人录制多路传感器数据用的容器格式，概念上类似"把好几路视频/传感器
日志按时间戳打包进一个文件"，读的时候可以按时间顺序把各路数据穿在一起重放）。

三种数据来源，殊途同归都写成 MCAP：

1. **合成数据**（`apps/synth_bag_gen`）：不需要真实水下环境，程序按配置好的一段
   轨迹（比如"沿半径 8 米的弧线走一段、深度 12 米"）用数学公式算出"如果机器人真的
   这么走，各个传感器理论上应该看到什么"，再叠加随机噪声模拟真实传感器的不完美，
   写成 MCAP。因为轨迹是自己算出来的，所以"标准答案"（ground truth，即真实轨迹）
   也是已知的——这让后面可以直接打分"算法猜得准不准"。这条路径最成熟、跑得最勤，
   也是仓库里绝大多数自动化测试用来验证代码有没有改坏的数据源。
2. **真实 HoloOcean 仿真录制**（`adapters/holoocean`）：HoloOcean 是一套第三方水下
   仿真软件（基于游戏引擎 Unreal Engine 5 搭建虚拟水下场景），可以生成比"数学合成"
   更接近真实传感器噪声特性的双目相机画面。仓库已经在真实 HoloOcean 环境里录过一段
   约 76 MB、50 帧的双目视频并转成了 MCAP。
3. **公开数据集转换**（`adapters/datasets`）：把别人发布的公开水下/机器人数据集
   （目前接入的是 EuRoC，一套常用的双目+惯导公开评测数据集）转换成同样的 MCAP 格式，
   用来验证这套系统的处理流程不是"只能吃自己生成的数据"，具有一定通用性。

### 第二步：回放处理管线——`apps/replay_demo` 到底做了什么

拿到一份 MCAP 之后，`replay_demo` 按时间顺序把里面的数据"喂"给下面这条流水线。
可以把整个过程想象成侦探破案：先分头收集各路线索（前端处理），再把线索整理成一条条
"约束条件"（因子构建），最后找一个和所有约束条件冲突最小的答案（优化求解）。

#### 2.1 声呐前端：从"一堆回波强度"里找出"目标点在哪"

声呐每次扫描发回来的原始数据是一长串"每个角度、每个距离上回波强度多大"的数字
（有点像老式雷达屏幕上那一圈亮暗不均的扫描线），需要从里面挑出"这是一个真实物体
反射回来的信号"，而不是背景噪声。这一步分三小步：

- **CFAR 检测**（Constant False Alarm Rate，恒虚警率检测）：一种从雷达/声呐领域
  借来的信号处理方法，简单说就是让检测门槛跟着周围背景噪声的强弱自动调整——背景
  吵的地方门槛抬高，背景安静的地方门槛降低，这样不管背景噪声大小如何变化，"误报
  一个不存在的目标"的概率都能维持在一个大致恒定、可控的水平，而不会因为某片区域
  特别吵就疯狂报假目标。
- **极坐标转换**：声呐原始数据是"角度+距离"这种极坐标形式，转换成更好处理的形式
  方便后续聚类。
- **DBSCAN 聚类**（一种"按点的疏密程度自动分组"的算法）：把散落的多个回波点，
  按"离得近的算一堆"的原则，聚成一个个"目标"，避免同一个物体的多个反射点被误认成
  好几个不同的目标。

这一段代码是从同事另一个仓库（`sonar_camera_reconstruction`）移植过来的（详见仓库
`NOTICE` 文件的版权说明），但**刻意没有**移植原版里"把检测结果直接换算到世界坐标系
里"的那部分逻辑——这是本仓库一条重要的设计原则：**前端只负责"看到了什么"，不负责
"猜自己在哪"**。也就是说，声呐前端说的永远是"某个东西在我正前方 2.3 米、偏右 15
度"这种相对自己的说法，而不是直接断言"某个东西在世界坐标系的 (10.2, 3.4) 位置"——
后一种判断需要先知道自己的准确位姿，而这正是整套系统要去求解的东西，前端不该先斩后奏。

另外，成像声呐这类设备通常只能测"距离+水平角度"，测不出"上下方向的角度"（叫
elevation，仰俯角）。这是这套系统里一个反复出现的边界条件：所有基于声呐的判断都
不会凭空编造一个高度信息出来。

> **代码怎么写的**：`include/frontends/cfar_detector.hpp` 里 `CfarDetector::Detect`
> 接收一张"[距离档 × 波束角]"的二维强度表（跟 `SonarFrame` 原始数据的排布一模一样），
> 逐个像素开一个滑动窗口做检测。CFAR 实际有四种变体可选（`CfarVariant`：`kCA`/
> `kSOCA`/`kGOCA`/`kOS`，分别对应几种不同的"怎么用窗口里的训练像素估计背景噪声水平"
> 的统计方法，仓库默认用 `kSOCA`），核心思路都是"拿这个像素周围一圈训练像素（隔开几个
> 保护像素，避免真实目标的能量泄漏进训练区把背景估计抬高）算出背景噪声水平，再乘一个
> 按预设误报率（`probability_false_alarm`，默认 0.1%）反推出来的系数，得到这个像素
> 专属的检测门槛"——这就是"门槛跟着背景走"在代码里的样子。`SonarCfarFrontend::
> ProcessSonarFrame`（`include/frontends/sonar_cfar_frontend.hpp`）接住检测掩码后转成
> 极坐标的候选点，再交给 DBSCAN（`dbscan_eps_m=0.2` 米、`dbscan_min_samples=2`，即
> "0.2 米内至少 2 个点才算一簇"）聚类成目标；这份代码是从 `sonar_camera_reconstruction`
> 的 `cfar.cpp`（四种变体的窗口检测逻辑）和 `CFAR.py`（门槛系数的推导公式）移植来的，
> 但极坐标转笛卡尔坐标、烘焙进世界系那部分被刻意留在了原仓库没有搬过来。

#### 2.2 光学前端：从两只眼睛的画面里算出"我这一小段是怎么移动的"

如果配置了双目相机（rig 里带相机），系统会跑一条叫 **VO**（Visual Odometry，
视觉里程计）的流程，作用类似"看着周围的参照物估算自己走了多远、转了多少"，是纯
靠视觉、不依赖 GPS 的一种相对位移测量方式。步骤大致是：

1. **特征点检测**：在左右相机画面里找一些容易被重复认出来的"标志点"（比如角点、
   高亮斑块），有两种检测方式可选（`bright_blob` 高亮斑块检测，适合合成数据里刻意
   打的高亮图案；`harris_corner` 角点检测，更适合真实图像的自然纹理）。
2. **立体匹配**：把同一时刻左右两个画面里的同一个特征点配对起来，靠视差算出这个点
   离相机多远（原理和人的双眼判断远近一样）。
3. **时序匹配**：把这一帧的特征点和上一帧的特征点对应起来，判断"同一个点这一帧比
   上一帧挪到哪儿了"。
4. **RANSAC 刚体拟合**（RANdom SAmple Consensus，随机抽样一致性）：一种"从一堆
   可能掺了错误配对的匹配点里，稳健地估算出真实运动"的统计方法——随机挑几组点算一次
   运动、看有多少其它点也支持这个答案，反复多次后留下"支持者最多"的那个答案，这样
   哪怕匹配点里混进了少量错误配对（比如把水草的两片叶子认错），也不会把最终结果
   带偏太多。

跑完这四步，就得到"相机从上一帧到这一帧，大致挪动了多少、转了多少"，附带一个
数值化的不确定度（协方差，说明这个估计有多可信）。

> **代码怎么写的**：这整条流程实现在 `include/frontends/stereo_landmark_vo_frontend.hpp`
> 的 `StereoLandmarkVoFrontend::Process`。它是**有状态**的——内部记着上一次调用时
> 三角化出的路标点（位置+外观小图块），所以每一帧必须按时间顺序喂给它，不能乱序或
> 跳帧调用。检测器按 `LandmarkDetectorKind` 二选一绑定（`kBrightBlob` 找合成场景里
> 特意画的高亮方块图案，配合仓库自己给每个路标烧的、按 id 唯一的哈希纹理；
> `kHarrisCorner` 是经典的角点检测算法，找真实图像里那些"往任何方向挪一点、局部
> 图案都会明显变化"的点，更适合没有人工特征的真实水下画面）；左右图之间、以及
> 相邻帧之间的匹配都由同一个 `PatchMatcher`（图块归一化互相关匹配，NCC）负责，只是
> 前者受"极线约束"限制（两个镜头是水平排列时，同一个点在左右图里应该落在同一行
> 附近，不必满屏搜索）。RANSAC 那一步在 `rigid_transform_fit.hpp` 里，用的是
> Kabsch/Procrustes 算法（一种给定两组配对好的 3D 点、直接闭式解出"怎么刚性挪动
> 才能让两组点对得最齐"的经典算法），RANSAC 只是在这外面套了一层"多试几种点组合、
> 挑支持者最多的那次结果"的稳健层。这里用的随机数种子（`rng_seed`，默认
> `12345`）是这个前端实例专属、构造后**永不重新播种**的——对应 `CLAUDE.md`
> 里反复强调的"随机数必须显式传入、跑到底不中途重播种"的纪律，这样"同一份录像、
> 同一份配置，跑两次结果必须完全一样"这条硬性要求才能成立。真实图像模式
> （`harris_corner`）还会主动收紧匹配容差参数（比如允许的行偏差 `max_row_diff_px`、
> 匹配分数的领先优势 `min_score_margin`）——仓库文档记录过一次真实教训：真实水下
> 纹理经常大片重复（比如成片的珊瑚礁纹理），参数放松后纯外观匹配曾把误差打到
> 587 米，收紧之后才恢复正常。

这条视觉路径也有它已知吃不消的场景：真实机体的左右相机如果不是严格并排安装（存在
一定的前后/上下偏移，而不是纯粹左右分开），做双目校正时需要施加一个不小的旋转来
"摆正"画面，这会把画面中心搬移，导致特征点检测/匹配的效果明显变差——这是目前
`README.md`「已知边界」里记录的一处真实短板，仿真合成数据上没有暴露，只有拿真实
录制的水下影像跑过一遍才发现。

#### 2.3 声光融合：让声呐和相机的判断互相印证

如果目标恰好同时落在相机视野和声呐扫描范围内，系统会额外跑一条"声光融合"支路：
把声呐检测到的一段弧（因为声呐测不出仰俯角，一个目标点实际对应"以声呐为圆心的一段
弧"，而不是精确的一个点）投影到相机画面里，看是否和相机识别出的目标区域重合，重合
就互相印证、算出一个更精确的深度值。这一支路的结果会单独进地图（下面会讲），但**不会
反过来影响机器人自身位姿的计算**——这是刻意的设计边界，避免"用还没验证过的联合判断
去干扰核心定位"。

> **代码怎么写的**：`include/frontends/acoustic_optic_associator.hpp` 的
> `AcousticOpticAssociator::Associate` 先做一道"审计优先"的时间同步检查——声呐和
> 相机的采集时刻如果差超过 `max_time_delta_s`（默认 0.05 秒）,直接拒绝，且把真实
> 的时间差记下来，**不会**先做几何计算再拒绝（先花算力算了半天再扔掉是浪费）。
> 通过时间检查后，把声呐那段弧按 `arc_samples`（默认 16 个采样点）离散化，逐点投影
> 到相机画面，用 `range_gate_m`（0.5 米）和 `bearing_gate_rad`（0.1 弧度）两道门槛
> 筛出候选，再打分排出名次。这里有个不直观但很关键的判断：如果排名第一和第二的候选
> 打分差距不够大（差距小于 `ambiguity_margin`），并不会立刻判"模糊、拒绝"——因为在
> 接近声呐正前方（boresight）的时候，仰俯角对方位角和距离的影响本来就很小，同一个
> 平面上采样出来的好几个候选点打分天然就会很接近，这不代表真的存在两个物理上不同的
> 候选点。只有当这两个候选的**深度值**也对不上（差距超过 `depth_agreement_sigma`
> ＝3 倍联合标准差）时，才真正判定为 `AMBIGUOUS`（模糊、需要更多信息才能确定）。
> 仓库文档特别提醒过：不要为了让某些测试场景"变绿"就删掉这道深度一致性判断，也不要
> 靠放宽 `ambiguity_margin` 让歧义判定消失——那是掩盖问题，不是解决问题。

#### 2.4 因子构建：把"线索"翻译成"约束条件"

前面几步分别产出了"相机看到的相对运动""声呐看到的目标距离""深度计读到的深度"这几类
"证据"。因子构建这一步，把每一条证据翻译成数学优化问题里的一条"约束"（术语叫
**因子**，factor；整体结构叫**因子图**，factor graph——可以理解成一张关系图，图上
每个节点是"某一时刻机器人在哪"，每条边就是一条约束，比如"这两个时刻之间大致挪动了
这么多""这个时刻离水面这么深"）。约束越多、彼此越吻合，最终解出来的答案就越准。

三类主要因子（代码都在 `include/factor_builders/`，每个因子本质是一小段"给定当前猜的
位姿，算出'和这条证据差多少'"的公式，这个"差多少"就叫**残差**，residual；因子构建
就是把每条证据包装成这样一段可计算的残差公式）：

- **相对位姿因子**（`relative_pose_residual.hpp`）：来自视觉 VO（或者最简单模式下，
  直接读取录制时预先算好的"标准答案+噪声"桩数据，这是给还没接视觉时先验证整条链路
  能不能跑通用的）。它的残差公式是"猜测的相对位移/相对转动"和"VO 实际测到的相对
  位移/相对转动"两者之差：位移部分是把猜测的两个关键帧位置换算到前一帧自己的视角下、
  再减去 VO 测到的位移；转动部分是拿猜测的相对转动和 VO 测到的相对转动做"差值"（用
  四元数——一种表示三维旋转、不会有万向锁问题的数学工具——的误差公式近似）。这里
  雅可比（残差随位姿变化的变化率，优化算法用来判断"往哪个方向调整能让残差变小"的
  关键量）是靠程序自动"数值微分"（把参数稍微挪动一点点、看残差变化多少）算出来的，
  不是手推的公式——省了手推公式出错的风险，代价是每算一次要多算 24 次残差，仓库
  文档里说明这是刻意的 v1 简化，等换成成熟求解器库后再优化成解析公式。
- **声呐距离因子**（`sonar_range_residual.hpp`）：残差公式就是"实测距离 − 猜测位置到
  附近路标点（们）平均位置的距离"。这里"附近路标点"从哪来是个关键设计：v1 版本的
  因子图里，图上的节点**只有关键帧位姿，没有把路标点也当成一起被优化的未知量**（这是
  文档里明确写的延后决策）；路标点位置是靠 `mapping::SubmapManager::QueryNearestPoint`
  查出来的、当作暂时固定不变的"外部上下文"喂给这条因子——查的时候拿"用当前死推算
  位姿把这次声呐检测投到世界系"的坐标去比对已经存过的路标，1.5 米内有命中就复用
  旧路标位置（比信任单次带噪声的新检测更稳），没命中就当新路标插进去。这条残差公式
  移植自 SVIn 那个仓库的 `SonarError`，但**雅可比是重新推导的**——原版的雅可比算法
  和这条残差公式在数学上并不精确对应（原版走的是声呐波束端点方向的近似路径），直接
  照抄会引入系统性误差，这也是 `NOTICE` 里专门记录的一处移植细节。
- **深度因子**（`depth_residual.hpp`）：残差公式最简单——"深度计测到的深度 + 猜测
  位姿的 z 坐标"（因为仓库约定世界坐标系是"z 朝上"，而深度计读数是"正向下"，两者
  符号相反，所以是加号而不是减号）。这条因子的意义比看起来重要：如果没有
  它，机器人往左右转、往前后走多少其实是"怎么标定都行"的相对量（专业说法是存在
  "规范自由度"，gauge freedom，意思是给整条轨迹统一平移/旋转一下，所有相对约束
  依然全部满足，因为它们描述的都是"相对关系"），但深度计读数是一个**绝对**的参照
  ——"我现在确实在水下 12 米"这种话没法靠"相对关系"绕过去，它把轨迹在上下方向上
  钉死到了真实世界的坐标系里。仓库文档里专门记录过一次真实踩过的坑：早期版本图的
  第一个节点被想当然地钉在"深度=0"，而其它节点又被真实深度证据往正确方向拉，两边
  打架，导致优化算法算了 30 轮都没收敛、最终误差高达 4.6 米——后来把第一个节点也
  改成用它自己的真实深度证据设初值才修好。这类问题单元测试测不出来，是靠真的跑一遍
  demo 才发现的（详见 `CLAUDE.md`「已经踩过的坑」，这也是这个仓库反复强调"改完代码
  一定要实跑一遍 demo，不能只信自动化测试全绿"的原因之一）。
- **回环闭合因子**（可选，默认关闭）：如果机器人绕了一圈又回到了曾经去过的地方，
  理论上应该能"认出"这是旧地方，从而把绕这一整圈积累的漂移误差修正回来——这就是
  "回环闭合"（loop closure）。做法是：拿当前位置去和之前走过的位置比对，位置足够
  接近的候选点里，再看画面里的视觉特征能不能真的对上，对上了就补一条"这两个时刻其实
  是同一个地方"的强约束。当前版本判断"位置足够接近"完全靠"死推算出来的坐标离得
  近不近"，还没有做"光看画面就能认出这是不是去过的地方"（这需要额外的图像检索技术，
  仓库里还没做，属于已知的功能边界，不算 bug）。

#### 2.5 优化求解：找一个让所有约束都"最不别扭"的答案

因子图搭好之后，交给一个数值优化算法去求解——目标是找一组轨迹点位置，使得"违反
每条约束的程度"加总起来最小。这类问题在机器人和计算机视觉领域统称"位姿图优化"
（pose graph optimization）。仓库默认用的算法叫 **Gauss-Newton / Levenberg-Marquardt**
（简称 GN/LM，两种关系很近的迭代优化算法，思路是"当前答案不满意 → 算一下往哪个
方向调整能让约束违反程度下降最快 → 挪一步 → 再检查满不满意 → 重复"，直到基本不再
改善为止，即"收敛"）。这是仓库自己用基础数学库（Eigen）手写实现的一版，**不是**
借用现成的成熟优化库；另外接入了一个可选的第三方求解器 Ceres 作为对照候选（工业界
常用的优化库），但目前刻意还没把默认值换过去——仓库的态度是"要不要换，得先用真实
基准测试数据说话，不能凭感觉觉得'手写的一定不如现成库好'就换"。

在默认的合成场景测试里，这个优化过程通常 4～7 轮就能收敛，最终轨迹和"标准答案"之间
的平均误差（下面讲的 ATE）大约 0.08～0.10 米。

> **代码怎么写的**：因子图本身用 `estimation/pose_graph_problem.hpp` 的
> `PoseGraphProblem` 表示——每个关键帧就是 7 个数字（三维平移 + 四元数的四个分量），
> 存在一个按插入顺序排列的表里；`AddKeyframe(..., fixed=true)` 可以把某个关键帧标记
> 成"锚点"，锚点不参与优化、永远保持初始值（这就是前面「⑤ warmup 窗口」那段提到的
> kf0：x/y/朝向可以锚在原点，但 z 必须锚在这一帧自己的真实深度证据上，不能想当然
> 锚在 0，否则会跟别的关键帧被深度证据拉扯的方向"打架"）。真正做数值迭代的是
> `estimation/gauss_newton_solver.hpp` 的 `GaussNewtonSolver`：每轮迭代都在算"往哪个
> 方向调整能让所有残差的加权平方和下降最快"，并且带了一个叫 `lambda`（阻尼系数）的
> 调节旋钮——如果这一步试探性调整让总残差反而变差了，就调大 `lambda`（迈更小、更
> 保守的步子）；调整成功了就调小 `lambda`（敢迈更大的步子）——这正是 Levenberg-
> Marquardt 相对纯 Gauss-Newton 的改进之处：纯 Gauss-Newton 步子太大时容易在某些
> 病态问题上"迈过头"甚至发散，LM 的阻尼机制让它更稳。回环闭合因子会被单独标记一个
> "稳健损失"策略（`RobustPolicy::kHuber`），意思是这条边如果残差特别离谱（很可能是
> 一次误匹配），优化算法会自动降低它的权重、不让一条可疑的边把整条轨迹带偏——其余
> 因子类型不挂这个标记，出多大的残差都按原样加权计入。

#### 2.6 地图与评测：算出"准不准"的分数

优化出轨迹之后，系统还会：

- 把声呐/相机看到的点云拼接成一份局部地图（有两种地图表示：一种是简单的点云子图
  `SubmapManager`；一种是更精细的、带置信度加权的 `SurfelMap`，SurfelMap 里每个
  "面元"不仅记录位置，还记录这块地图证据的可信程度，可以随着更多观测逐渐修正、
  剔除明显是噪声的离群点）。
- 算精度打分：最主要的指标叫 **ATE**（Absolute Trajectory Error，绝对轨迹误差）
  ——把算出来的轨迹和"标准答案"逐点对比，算出平均偏差多大（单位：米），数字越小
  说明算得越准。

> **代码怎么写的**：地图这一层（`mapping/submap_manager.hpp` 的 `SubmapManager`）
> 有一条和前面"前端不猜自己在哪"呼应的设计原则：每份地图证据存的时候永远是**相对
> 于它所属那个关键帧的局部坐标**，从不在存入的那一刻就换算烘焙成世界坐标系下的固定
> 位置。要看某个关键帧的地图点在世界坐标系里到底在哪，得调用
> `WorldPointsForKeyframe`，它每次都用这个关键帧**当前最新的位姿**现算一遍。这样
> 设计的好处是：一旦优化求解器后来修正了某个关键帧的位姿（比如因为后面又多测到了
> 一条回环边），地图点的世界坐标会自动跟着"更新"，不需要重新跑一遍前端、也不需要
> 谁手忙脚乱地去改已经存好的地图数据——这正是前面提到的"`sonar_camera_
> reconstruction` 的 `merge.py` 一进来就把点烘焙进世界坐标系"这种做法被刻意规避掉的
> 原因：烘焙得太早，后面位姿一修正，地图就跟丢了。

跑完之后，`replay_demo` 会输出一份轨迹文件、一份记录"这次跑的用的是什么配置、什么
代码版本、什么随机种子"的运行清单（`RunManifest`，方便日后复现这次结果），并根据
预先设好的及格线（比如"误差不能超过多少米""优化必须收敛"）判断这次跑得算不算合格，
不合格会让整个流程报错退出——这样自动化测试就能拿它当"及格线"用，而不是靠人工去看
数字。

### 现状小结

合成数据这条路径已经完全跑通，而且有"确定性回放测试"守着——同一份数据、同一份
配置，跑两遍必须得到一模一样的结果，一旦哪次改动让结果变得不可复现，测试会立刻
报错。真实 HoloOcean 录制的数据也能进入这条流水线，但受限于上面提到的双目校正
主点偏移问题，目前误差还比较大（约 4.3 米），优化没能收敛到令人满意的程度——
这是已知且已经定位到根因、但还没修复的短板，不是"没试过"。

## 主线二：ROV 在线驾驶辅助（实时闭环，进行中）

### 一句话概括

主线一是"录完再算"，主线二是"边走边算、当场给驾驶员提示"。目标场景是操作员实时
遥控 ROV（这里具体设定为 BlueROV2 Heavy 这款机体，配 AI-D 双目相机和 SV1213 成像
声呐）在水下执行任务时，系统实时把声呐和相机看到的目标识别出来、跟踪住，实时提示
操作员"目标在哪个方向""系统现在状态健不健康"，操作员据此调整操作；同时留了一个
"脚本飞手"接口，可以让程序自动生成推进器指令，模拟无人自主驾驶的场景。

**这条主线目前只验证到"代码写完、单元测试和不需要真实仿真器的冒烟测试都通过"这一
步，还没有在真正的 HoloOcean+UE5 仿真器上完整跑过一次端到端闭环**——因为开发这套
系统所用的这台 Linux 机器没有装 HoloOcean/UE5（这套仿真软件官方主要支持 Windows）。
换句话说：单个零件都测过能转，但整台机器还没有真的启动运行过一次。

### 数据是怎么流动的

按 README 里的图，整个闭环由若干各自独立、可以分别启动/重启的程序组成，靠 ROS2
（一套机器人领域常用的"进程间消息总线"中间件，各程序把消息发布到一个个"话题"
topic 上，别的程序订阅这些话题就能收到）互相传消息：

1. **仿真环境**（HoloOcean / UE5）：在虚拟水下场景里跑物理仿真，产出左右相机画面、
   声呐扫描帧、姿态/惯性/深度传感器读数等"原始传感器信号"。
2. **`realtime_ros_session`**（Python 程序）：每一个仿真时间步（tick）都去问仿真器
   "现在各传感器看到什么"，把结果转换成规范格式发布到几个约定好的 ROS2 话题上
   （左相机、右相机、声呐、车辆状态四个"算法能看到"的话题，外加一个单独给操作员看
   画面用的"驾驶员相机"话题——这两类话题是刻意分开的，算法只能看前四个，不许碰
   驾驶员专用的画面通道）。它还负责接收"推进器该往哪转"的指令，转发回仿真器，让
   虚拟 ROV 真的动起来，形成闭环。
   - 值得一提：这里的"车辆姿态"是靠姿态传感器+惯性传感器+深度传感器**拼凑组合**
     出来的估计值，系统**永远不允许**直接读取仿真器提供的、上帝视角式的"绝对真实
     位姿"——这是为了让实时闭环用的信息和真实机体在真实水下能拿到的信息保持一致
     （真实机体当然也没有上帝视角）。这条规则在代码里的唯一出处是
     `uw_holoocean_adapter.ros_message_conversion.build_topic_map()`：它明确定义了
     算法侧只允许订阅的四个话题（左右相机、声呐、车辆状态），单独给"驾驶员画面"和
     "仿真器真值"开了另外两个不在算法允许清单里的话题，从源头上让算法代码根本没有
     机会不小心读到真值或驾驶员专属画面。
3. **`holoocean_realtime_node`**（C++ 程序，"实时网关"）：订阅上面那四个算法话题，
   把 ROS2 消息转换成仓库自己的统一消息格式，送进后面的处理管线；处理完的结果再
   转换回 ROS2 消息，发布出去给操作员界面和自动飞手用。
4. **`LiveEventSource`**（进 C++ 网关内部，一个"四车道排队系统"）：实时数据不像离线
   文件那样能"停下来等你处理完"，如果处理跟不上传感器发送的速度，就得有个策略决定
   "先处理谁、丢弃谁"。这里把不同种类的数据分成四条独立的"车道"（打个比方类似高速
   公路上分了四条车道，各自限速、各自的应急车道规则都不一样）：
   - **定位车道**（车辆姿态数据）：宁可让发送方等一等（拒绝新数据，逼上游知道"我
     处理不过来了"），也不能悄悄丢定位数据，因为定位是最基础的信息。
   - **修正车道**（声呐数据）、**建图车道**（相机数据）：这两类数据处理起来比较
     "费时"（要跑目标检测），所以给它们设了"数据超过一定时长还没处理就直接丢弃"
     的规则——一条声呐数据如果已经过时到"就算处理完也没意义了"，那还不如不处理，
     省下的算力处理更新的数据。
   - **证据车道**：处理成本低、不那么紧急的数据，队列满了就丢最旧的，不阻塞。

   这套排队系统还会持续统计"每条车道现在积压了多少""数据从进队到被处理平均/最坏
   等了多久"，这些统计数字直接决定了后面「四档 gate」小节里的验收标准过不过关。

   > **代码怎么写的**：实现在 `include/runtime/live_event_source.hpp` 的
   > `LiveEventSource`，四条车道各自的默认容量/溢出策略/"最长能等多久"写在
   > `LiveSourceConfig` 里——定位车道 64 条容量、`kReject`（队满就拒收新数据，逼
   > 上游明确知道"我已经跟不上了"）、不设等待上限；修正车道（声呐）32 条容量、
   > `kDropOldest`（队满就先丢最旧的，给新数据腾位置）、最多在队列里等 0.5 秒；
   > 建图车道（相机）16 条容量、同样 `kDropOldest`，也是 0.5 秒上限；证据车道
   > 256 条容量、`kDropOldest`、不设等待上限。0.5 秒这个数字不是拍脑袋定的，
   > 代码注释里写明是对齐了系统自己规定的"结果最多能陈旧多久"的硬性上限——一条
   > 已经等了超过这个时长的声呐/相机数据，就算马上处理完，结果也早就没有意义了，
   > 那还不如在出队之前直接丢掉，把算力省给还有意义的新数据（这个判断在数据真正
   > 被取出处理**之前**做，而不是先处理完才发现"晚了"，那样处理这一步的算力就白
   > 花了）。定位车道之所以选择"宁可拒收也不静默丢"而不是"超时丢弃"，是因为姿态
   > 数据是最基础的输入，丢了会让别的判断都失去参照，代码里专门用注释说明了这条
   > 取舍的理由。

5. **`OnlineAssistPipeline`**（在线辅助管线，处理核心）：这是主线二真正"算东西"的
   地方。和主线一那套"因子图+优化求解"完全不同，它做的是更轻量的**目标检测 + 跨
   模态关联 + 目标跟踪**：
   - 视觉和声呐两路目标检测**完全独立运行**，谁都不依赖谁——如果声呐信号突然
     中断，视觉这一路照样继续跟踪目标并给出提示，反之亦然。这是刻意的设计目标：
     宁可"降级但还能用"，也不要"一个传感器出问题就整个系统罢工"。

     > **代码怎么写的**：这条原则直接写在 `include/application/online_assist_pipeline.hpp`
     > 的头注释里——"稠密立体深度是唯一被卡预算的路径，因为它是唯一真正昂贵到需要
     > 实时预算决策的计算"，言下之意是其余检测/关联/跟踪逻辑都足够轻量，不需要靠
     > "互相等待"来保证不出错，独立跑反而更稳。实现上，`OnlineAssistPipeline::
     > OnImageFrame` 和 `OnSonarFrame` 是两个各自独立的入口，谁先到就先跑谁的检测；
     > 视觉检测结果不会立刻单独触发一次"关联+发布"，而是先存起来等下一次声呐数据
     > 到达时一起做跨模态关联（声呐是关联批次的正常触发者）——但如果检测到声呐确实
     > 掉线了（超过 `modality_stale_after_s`，默认 1 秒没收到新的声呐数据），就会
     > 转为让视觉检测立即单独触发一次发布，不会因为等不到声呐就让操作员一直看不到
     > 最新的视觉提示。系统的"健康状态"判定也是分层的：单独一路传感器掉线只报
     > "可疑"（SUSPECT）而不是"不可用"（UNAVAILABLE），并且明确保证这时候给操作员的
     > 提示依然有效（`guidance_valid=true`）——只有两路都死了，或者车辆自身姿态数据
     > 都过期了，才会真正报"不可用"。
   - 视觉这一路先用 HSV（一种按"色调/饱和度/亮度"描述颜色的方式，比 RGB 更贴近
     人眼判断"这是不是同一类颜色"的直觉）颜色阈值找出可能的目标区域，再看看画面里
     有没有养殖网箱、管线这类结构性线条来估计"我相对预定路径偏了多少"。

     > **代码怎么写的**：`adapters/opencv/include/adapters/opencv_visual_assist_frontend.hpp`
     > 的 `OpenCvVisualAssistFrontend`。目标检测部分是"色调在 45～85 度之间、饱和度
     > /亮度不能太低、连通区域面积至少 500 像素"的 HSV 阈值分割（这个色调区间大致
     > 对应绿到青蓝色系，是给养殖网箱这类特定颜色场景调的参数，不是通用颜色检测）。
     > 路径偏移估计部分用 Canny 边缘检测 + 霍夫直线变换找出画面里成片的、方向一致的
     > 结构线（比如管线、网箱边框），再折算成"我偏离参考路径大约多少米"。这里有一整套
     > **宁可拒绝也不凑合**的质量把关：亮度太低、对比度太低、画面模糊（用拉普拉斯
     > 方差衡量清晰度，数值越低说明画面越糊）、找到的结构线支撑度不够，任何一条不
     > 达标就直接报告"这次检测不可靠"，而不是硬凑一个可能是错的答案糊弄过去——代码
     > 注释里明确说这是"fail-closed"（宁可明确说'不知道'，也不要悄悄给错答案）的
     > 设计取向。
   - 视觉检测到的目标和声呐检测到的目标，如果方向、时间都对得上，会被"关联"成
     同一个目标的两路证据（跨模态关联，逻辑上和主线一的"声光融合"是同一类思路，
     但这里不涉及位姿图，只是给同一个目标打上"视觉也看到了、声呐也看到了"的
     标签，提升可信度）。

     > **代码怎么写的**：`include/frontends/target_associator.hpp` 的
     > `TargetAssociator::Associate` 把每一次候选配对推过一串门槛依次检查：输入
     > 数据本身有没有问题 → 两个传感器的标定版本对不对得上 → 坐标系能不能解析
     > → 采集时间差够不够近 → 目标类别兼不兼容 → 各自的测量不确定度是否在可接受
     > 范围内 → 方位角/距离/两者联合的统计距离（马氏距离，一种"考虑了不确定度大小"
     > 的距离度量，同样的数值差，测得越准的传感器容忍的偏差应该越小）是否超标 →
     > 运动是否连续（这一帧和上一帧比，目标不能瞬间跳到不合理的地方）。任何一步没
     > 通过都会带着一条结构化的"哪个指标、实际值多少、门槛多少"的诊断信息被拒绝
     > 记录下来，而不是简单丢一个"失败"了事——这样排查"为什么这次没关联上"时能
     > 直接看诊断，不用去猜。
   - **目标跟踪**：给每个目标维护一个"航迹"，新的一帧检测到的目标要和已有航迹配对
     （配对不上太多次就判定这个目标丢了，连续没检测到会被判定"已过期"从列表里
     移除，短暂丢失会靠运动模型简单预测补几帧，不会一失踪就立刻从提示里消失）。

     > **代码怎么写的**：`include/frontends/target_tracker.hpp` 的 `TargetTracker`
     > 给每个目标维护一个 4 维状态（方位角、方位角变化速度、距离、距离变化速度）
     > 加一个 4×4 的不确定度矩阵，新检测靠马氏距离门控（阈值 16，同样是"越不确定的
     > 匹配越难通过"的思路）配对到已有航迹上。默认参数：连续命中 2 次才把一条航迹从
     > "待确认"提升为"确认"（`confirm_hits=2`，避免一次噪声误检测就冒充成一条正式
     > 航迹）；连续 3 次没检测到就把航迹标记降级（`degraded_misses=3`）；0.5 秒没更新
     > 就标记为"陈旧"（`stale_after_s`），不再拿它去指导操作员，但也不立刻删除——
     > 真正把它从内存里彻底清掉是等到 5 秒都没更新（`retention_after_s=5.0`）才做，
     > 这个数字特意留得比"陈旧"宽松很多，为的是目标只是短暂被挡住又重新出现时，能
     > 接上原来的航迹编号继续用，而不是每次都当成一个全新目标、编号一直涨。整批
     > 检测数据是"原子"更新的：只要这一批里有任何一条数据非法或者顺序不对，整批
     > 全部作废、不留下部分更新的中间状态，避免因为一条坏数据把内部状态搞乱。
   - 稠密立体深度（更精细的"整幅画面每个像素多远"，而不只是"检测框大致多远"）是
     唯一一条被"要不要跑"严格卡预算的计算——因为块匹配这类稠密计算比较费时间，
     系统会检查"这一轮的时间预算还够不够"，不够就直接放弃这一轮的稠密计算，绝不
     让它拖慢其它更重要的处理，超预算和算失败对外表现完全一样，都算"这次没跟上"。
   - 系统会持续判断自己现在处于什么"健康状态"（完全正常 / 某个传感器暂时不可用但
     还能凑合用 / 完全不可用需要操作员接管），并把判断依据和原因一起发布出去，而
     不是只给一个笼统的"正常/异常"。

6. **HMI 叠加图层 + 状态消息**（HMI = Human-Machine Interface，人机界面）：处理
   结果会渲染成一张叠加在驾驶员画面上的图（标出识别到的目标、航向偏移箭头、健康
   状态横幅），加上一份机器可读的状态数据，一起发布出去给操作员的显示界面和下面的
   自动飞手用。
7. **脚本飞手**（`scripted_pilot`）：一个简化版的"自动驾驶逻辑"（不是正式的自主
   导航产品，只是用来测试闭环能不能真的转起来），订阅上面的状态消息，如果状态过时
   太久或者判断为"无效"，就直接把推进器指令全部归零（不瞎猜、不硬冲），否则按照
   看到的目标方向生成简单的转向/前进指令，发回给仿真器。
8. **故障注入**（`fault_injector`）：为了在没有真实故障的仿真环境里也能测试"系统
   遇到丢帧、重复帧、乱序、断流、推进器降效这些异常情况会不会正确降级"，专门写了
   一个按设定好的随机种子提前生成"什么时候该出什么故障"的调度器，运行时按计划注入
   这些异常，而不是真的等运气不好才能测到。
9. **任务评分**（`task_scorer`）：这是**全系统里唯一被允许看到"仿真器里的绝对真实
   位置"的模块**（其它所有模块都不能看，理由同上——要保证算法侧看到的信息和真实
   水下机体能拿到的信息一致）。它拿真实位置和算法输出的目标位置/航向偏移做对比，
   算出识别的准确率/召回率、误报频率、角度和距离误差的统计量、任务有没有完成、
   花了多久完成等一整套打分指标。

### "四档 gate"是什么

Gate 在这里指"验收门槛/及格线"。系统预设了四种不同严苛程度的场景剧本（对应四份
配置文件）：

- **minimum**（最低配）：要求最宽松。
- **nominal**（标称/正常）：日常预期的运行工况。
- **disturbed**（有干扰）：故意开启故障注入，模拟传感器时不时抽风的情况。
- **overload**（过载）：故意加重负载，测试系统扛不扛得住极限情况。

每一档都规定了"结果最多能有多陈旧""处理延迟的最坏情况（P95，即 100 次里最慢的
第 5 次也不能超过多少）不能超过多少毫秒""允许丢结果/漏报的比例上限""内存占用增长
不能超过多少""CPU/GPU 还得留多少余量"等具体数字。跑一遍对应场景，拿实测数据和这些
门槛比对，过了算合格。

### 目前的边界

代码层面这条主线已经完整实现，包括：Python 侧的仿真会话管理、C++ 侧的实时网关、
故障注入、任务评分、四档验收脚本，并且各自都有对应的单元测试；不需要真实仿真器
就能跑的两个"冒烟测试"（用合成的、但走真实处理逻辑的数据模拟传感器高速流入，检验
排队系统和处理管线在这种节奏下表现是否正常）也都能在普通开发机上跑通。**但**真正
让 HoloOcean/UE5 仿真器、真实的 ROS2 Python 库（rclpy）跑起来、把上面九个步骤串成
一个真正的端到端闭环——因为开发所用的这台机器没装这两样东西——还没有被实际跑过。
代码写得再完整，也不能等同于"验证过真的能用"，这是仓库文档里反复强调、要如实说明
的一点。

## 两条主线的关系：一张对照表

| | 主线一：离线 SLAM | 主线二：ROV 在线辅助 |
|---|---|---|
| 什么时候用 | 事后分析、调参、打精度分数 | 作业过程中，实时提示操作员 |
| 数据从哪来 | 一份录好的 MCAP 文件，一次性顺序读完 | 实时传感器流，源源不断进来 |
| 核心算法 | 因子图 + 数值优化，求一条最吻合所有证据的完整轨迹 | 目标检测 + 跨模态关联 + 跟踪，不做位姿图优化 |
| 输出 | 一条轨迹 + 一份地图 + 精度打分 | 实时的"目标在哪、系统健不健康"提示 + 画面叠加图 |
| 复用的部件 | 声呐前端、光学深度前端等 | 和主线一**共用同一份**声呐前端等前端代码 |
| 对"结果必须完全可复现"的要求 | 硬性要求——同样输入必须逐字节得到同样输出 | 尽量确定性（随机数都显式可控），但不强求逐字节一致 |
| 当前成熟度 | 合成数据完全跑通、有自动化回归测试守着；真实录制数据还没调通 | 代码和各模块的测试都完成；还没有在真实仿真器上完整跑通一次 |

两条线共用的东西，也是这个仓库最基础的两条"地基"：

1. **同一套跨语言消息格式**（用 Protobuf 定义，一种谷歌开源的、给不同编程语言之间
   传递结构化数据用的规范，好处是 C++ 和 Python 两边永远用同一份"字典"，不会出现
   "C++ 这边字段叫这个名字，Python 那边理解成别的意思"这种错位）。
2. **同一个数据入口接口**：不管数据是从文件里读出来的，还是实时流进来的，最终都会
   被整理成同一种"标准事件"格式，喂给下游同一套接口。这意味着"从离线切换到实时"
   本质上只是换了一个数据来源，而不是重写一遍下游逻辑——这也是为什么仓库能保证
   两条主线用的是"同一套地基"，而不是两个各自为战的系统。

## 附：一次性说明本文出现过的专业术语

| 术语 | 大白话解释 |
|---|---|
| SLAM | 一边估计自己的位置和姿态、一边把看到的环境拼成地图 |
| ROV / AUV | 遥控/自主水下机器人 |
| 声呐 | 靠发射声波、接收回波判断距离的传感器，水浑时比摄像头可靠，但一般测不出上下角度 |
| VO（视觉里程计） | 靠比对连续画面里参照物的变化，估算自己挪动了多少 |
| MCAP | 一种把多路传感器数据按时间戳打包进一个文件的录制格式 |
| Protobuf | 一种跨编程语言的结构化数据格式定义方式，保证不同语言对同一份数据的理解一致 |
| CFAR | 一种让检测门槛跟着背景噪声强弱自动调整的信号检测方法，控制误报率 |
| DBSCAN | 一种按点的疏密程度自动分组（聚类）的算法 |
| RANSAC | 一种在混有错误数据的一堆点里，稳健找出"大多数点都支持"的答案的统计方法 |
| 因子 / 因子图 | 把一条观测证据翻译成"轨迹上两点/一点应该满足的约束条件"，所有约束条件连起来构成一张图 |
| 位姿图优化 / GN/LM | 在因子图上找一组位置，让"违反所有约束的程度"加总起来最小的数值算法 |
| 规范自由度（gauge freedom） | 只有"相对关系"约束时，整条轨迹平移/旋转不会破坏任何约束——所以必须靠深度这类"绝对"约束把它钉死 |
| 回环闭合 | 机器人绕一圈回到走过的地方，靠"认出旧地方"消除整圈积累的漂移误差 |
| ATE（绝对轨迹误差） | 算出来的轨迹和标准答案之间的平均偏差，数字越小越准 |
| ROS2 | 机器人领域常用的"进程间消息总线"，不同程序靠订阅/发布话题互相通信 |
| HMI | 人机界面，这里指给操作员看的状态提示和画面叠加 |
| Gate（验收门槛） | 一组预先定好的及格线，实测数据达标才算这次跑合格 |
| P95 | 100 次里最慢的第 5 次的水平——常用来衡量"最坏情况"，比平均值更能反映系统的稳健性 |
| 残差（residual） | "猜测值"和"实际测量值"之间的差；优化算法的目标就是把所有残差加权平方和调到最小 |
| 雅可比（Jacobian） | 残差随参数变化的"变化率"，优化算法靠它判断这一步该往哪个方向、调整多少 |
| 四元数 | 一种表示三维旋转的数学工具，比欧拉角（俯仰/偏航/横滚角）更稳定，不会出现"万向锁"（某些角度组合下丢失一个自由度）问题，本仓库统一用它、不用欧拉角 |
| 马氏距离 | 一种"考虑了测量不确定度大小"的距离度量：同样的数值偏差，测得越准的地方容忍的偏差应该越小，比直接算欧氏距离更合理 |
| 阻尼系数（lambda） | LM 优化算法里的一个"步子大小"调节旋钮，这一步走顺了就调小、敢迈大步，走歪了就调大、变保守 |
| HSV | 一种按"色调/饱和度/亮度"三个维度描述颜色的方式，比"红绿蓝"三通道更贴近人眼判断颜色的直觉 |
| fail-closed | 一种设计取向：条件不满足时宁可明确报告"这次不可靠/拒绝"，也不要凑一个可能是错的结果糊弄过去 |
